What it does

After the visit, the technician just talks

One voice session replaces the write-up — and ends as evidence, not as audio.

1

Consent first

Visible consent screen before the mic ever opens; session only on an explicit tap.

2

Live interview

Raw WebSocket to the AssemblyAI Voice Agent API. One thing at a time; VAD tolerant of working pauses; barge-in enabled.

3

Card fills live

Every statement becomes a client-side JSON-Schema tool call. Each field carries its own audit trail: which tool set it, when, voice-confirmed or hand-edited.

4

Read-back loop

Critical values — services, severity, timeline hours — are spoken back and confirmed before they count.

5

Evidence out

CSV for the ticket system, print-ready PDF, and a JSON timeline artifact powering replay + metrics. Audio discarded by design.

Why after the visit: live voice during the repair was tried and gated out by evidence — a pre-registered 10 dB noise gate failed every criterion (runbook and results committed). The pivot is documented, not hidden.

Architecture

One engine, two channels, zero npm dependencies

Static browser app with no build step; a DOM-free session engine shared by browser and Node — which is what makes the pipeline CI-able.

Browser — static, no build

  • Raw WebSocket to the AssemblyAI Voice Agent API — contract verified from official docs; no SDK exists for the web, so we wrote the client
  • Tools defined client-side with JSON Schema + catalog enums — the agent can only pick services that exist
  • Incident state + per-field audit trail + artifact builder
  • Audio: memory only — never disk, never upload

Serverless — Vercel

  • api/token — issues one-use temp tokens; the API key never reaches the browser
  • api/sessions — stores transcript + tool state, never audio; rejects artifacts claiming otherwise

Mock channel — CI

  • Same interface as the real channel; deterministic rule-based interviewer
  • npm run selftest + npm run smoke:mock = the whole CI
  • Node 22, ESM, zero runtime deps
The incident product was a pivot: ~70% of the code (channel, engine, artifact, metrics, export) is shared with the original work-order variant, which remains in the repo with its noise-gate evidence.

The core mechanism

Confusables are caught twice

The schema rejects what cannot exist; the spoken loop rescues what exists but is wrong.

Catch 1 — catalog enum in the schema

A service the catalog does not define is rejected before the read-back even asks. The agent cannot invent entries; services set precision across the 10 real sessions: 100% (12 TP / 0 FP).

Catch 2 — the spoken read-back

Real-but-wrong values survive the schema — that is what the loop is for. Read-back precision (read-backs that caught a real error): 62.1% over 29 read-backs in real dialogue.

"did you say production? the catalog also has staging — which one was it?"

A seeded capture error, rescued in a real session

Rack A8 captured → disambiguation read-back naming both catalog services → operator confirms A3. Recorded in the session artifact (committed as evidence): gate_R5d, script i4.

Under the hood

A measured prompt fix, not a vibe

Same scripts, same conditions — only the interview prompt changed, and the numbers moved.

The collapse (v3)

Pure-narrative capture — continuous dictation, no pauses, no markers — ended in 1 tool call and 0/8 timeline hours, twice in a row. Services recall 37.5%, hour-exact timeline 35.3%, severity 2/5, EOS→tool p50 1,775 ms.

The fix (v4) — a "registrar" reframe

One rule set: no spoken datum goes unregistered, one tool call per datum, read-back grouped at the close, hour-conversion few-shots ("eight fifty" → 8:50).

The result

Services 100%/100% precision/recall (9 TP / 0 FP / 0 FN) · timeline hours 72.2% (13/18) · severity 4/5 · EOS→tool p50 1,139 ms. The collapsed script now registers 10–15 tool calls and 7/8 hours.

WER is 0.231 in both halves — the fix changed tool-call discipline, not hearing. That is the point: the loop, not the transcriber, carries correctness.

And the discipline about the discipline: a v5 attempt (three targeted edits) regressed in its only measured run — read-backs spoken without tool calls — and was fully reverted. The two-iteration budget was pre-registered and exhausted; the variance is documented, not iterated away.

Honest rig & framing

The limits, published with the numbers

Everything below is in the README and the submission text — the failures are part of the deliverable.

  • WER 0.231 on matched pairs — roughly one word in four. Not hidden; it is the reason the product is a confirmation loop and not a transcriber.
  • The rig is rules-only: scripted operator utterances at natural pace, seeded ground truth, no free-form human turns. Reproducible numbers — and no claim of spontaneous-conversation performance.
  • 2 of 10 sessions hit the 300 s driver watchdog and lost their final turns — one severity miss is the correction turn that never played.
  • 0 of 10 reached enviar_reporte — the rig closes the socket after the last scripted reply, so the report status stays in-process in every artifact.
  • Designed barge-ins never made the 500 ms window: 0/3 (1,338 / 9,034 / 20,501 ms) with interruption configured throughout — the same weakness that failed the 10 dB noise gate and drove the post-visit pivot.
  • Run-to-run variance persists — one v4 session spoke read-backs without registering the timeline. v4 mitigates; it does not eliminate.
